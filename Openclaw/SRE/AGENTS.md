## 变更与发布

### 变更前

- 明确变更单、目标环境、维护窗口、依赖项和回滚触发条件。
- 检查当前健康度、容量余量、告警状态和近期关联变更；异常状态下不叠加常规变更。
- 对 IaC、Kubernetes YAML、Helm、Terraform 或脚本修改，先做静态校验和差异审查。
- 生产变更默认采用灰度或分批策略；先选择影响最小且可观测的范围。

### 变更中

- 一次只引入一个可归因变量；记录实际开始时间、执行人和关键命令。
- 持续观察错误率、延迟、饱和度、可用性、业务成功率和资源容量。
- 达到回滚阈值立即止损，不在故障期间继续叠加未经验证的修复。

### 变更后

- 用预先定义的指标和用户路径验证结果，不以“命令执行成功”代替服务恢复。
- 记录结果、剩余风险、配置差异和后续待办；清理临时权限与临时资源。

## 事件响应

### 分级原则

- P0：核心生产服务大面积不可用、数据丢失风险或安全事件。立即止损、升级、建立事件时间线。
- P1：重要功能显著受损或容量临界，存在扩散风险。优先缓解并明确恢复目标。
- P2：局部影响、可绕过或不影响 SLO。纳入排期处理，避免抢占 P0/P1 资源。

### 标准流程

1. 确认：核实告警是否真实，量化影响用户、服务和地域/集群范围。
2. 控制影响：停止高风险变更，采取最小、可回滚的缓解措施。
3. 定位：按时间线关联指标、日志、事件、部署与依赖变化，保留原始证据链接。
4. 恢复：以 SLO、关键业务链路和容量余量确认恢复。
5. 复盘：在不指责个人的前提下记录根因、促成因素、检测缺口和行动项。

### 对外状态更新

每次更新应包含：

- 当前影响与已知范围。
- 当前处置动作和效果。
- 已确认原因或明确标注“仍在调查”。
- 下一次更新时间（北京时间）。

不猜测根因，不承诺未验证的恢复时间。

## Kubernetes 与云原生

- 先确认目标集群与 namespace，再查看 `Deployment`、`StatefulSet`、`DaemonSet`、Pod、Event、HPA、PDB、NetworkPolicy 和 Ingress/Gateway。
- 排障顺序通常为：调度与事件 → Pod 状态与探针 → 容器日志/重启原因 → 网络与 DNS → 存储 → 上游/下游依赖 → 节点与集群控制面。
- 处理异常 Pod 前，先确认其控制器、副本数、PDB、流量入口和是否有状态；不得默认删除或驱逐。
- 使用 `kubectl` 时显式传入 `--context` 和 `-n`。生产环境禁止无选择器的大范围操作，例如全 namespace 删除、全节点 drain 或批量 rollout restart。
- 修改资源配额、限额、HPA 或副本数前，评估节点可分配资源、PDB、自动扩缩容行为和成本影响。

## GPU 与 AI 平台

- 优先确认影响的是训练、推理、调度、驱动、节点硬件还是网络/存储链路。
- GPU 异常按以下层级收集证据：
  1. 工作负载：Pod Event、容器退出码、训练/推理日志、CUDA/NCCL 报错。
  2. Kubernetes：调度事件、资源请求与限制、Device Plugin、节点污点/标签、GPU Operator 状态。
  3. 节点：`nvidia-smi`、DCGM 指标、GPU 温度/功耗/ECC、内核日志中的 `NVRM` 与 Xid。
  4. 基础设施：网络、RDMA/IB、存储、供电与宿主机健康度。
- Xid 等硬件/驱动事件以受影响节点的内核日志为准；DCGM 或 exporter 指标用于关联和告警，不替代原始驱动记录。
- 在未确认影响范围前，不重启 GPU 节点、不重置 GPU、不驱逐训练任务。先保留日志、作业 ID、节点状态和发生时间。
- 对分布式训练，核对所有 rank 的失败时间、NCCL 拓扑、网络错误及是否存在单节点异常，避免把集群问题误判为单个任务问题。

## 可观测性与 SLO

- 使用 RED（请求率、错误率、时延）和 USE（利用率、饱和度、错误）组织排障视角。
- 告警应可行动：包含对象、环境、阈值、持续时间、影响、仪表盘和 Runbook 链接。
- 优先处理用户可感知的 SLO 违规与错误预算消耗；单一资源指标异常需结合业务影响判断优先级。
- 仪表盘和查询要写明时间范围、聚合维度、采样限制与缺失数据的含义。
